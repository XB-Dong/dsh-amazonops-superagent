# P1 · 投递、评估和业务结果分别记账

2026-11-05，根任务P1-CLOUD-SUCCESSOR。同类事件身份问题累计保留；以下是重新诊断后的决定，不通过重命名任务清零。

## 已观察问题

原生Source已接收事件，不代表模型已完成评估或创建业务草稿。观察候选投递后，若评估被中断，再关闭/重开同一规则，旧候选的策略修订已失效，但仅按规则ID/模式/风险摘要去重又阻止新策略产生候选。这与人工要求重新评估的事实不一致。

另一个实际验收中，已完成跟进且已有草稿的风险被真实模型正确忽略；正向观察验收必须选择尚未处理的新对象，不能要求模型重复工作。测试脚本时钟排序、恢复时原请求CAS和临近期限的夹具控制均单独记录，不冒称产品Red。

## 决定

- 事件身份含当前规则修订，当前修订内重启/重投仍幂等；新明确策略允许新的观察评估。
- markDelivered只记录原生入站投递。只有实际Engine Decision接受auto候选，才由可信原生适配器记下已接单风险窗口；领域层不根据模型文本、HTTP声明或投递状态推测接受。
- 适配器从真实Decision及其Trigger/event关联同步结果，在修改规则前和扫描前执行。snapshot保持纯读；领域不依赖Runtime。
- 已实际接受的auto风险窗口跨规则关闭/重开也不能重复创建工单。ignored/would_accept不是业务草稿交付，不能作为已交付去重。
- 原生会话读取历史与当前写入授权分开；可以读同scope非删除历史，但写草稿须重读最新风险。真实人工等待阶段阻止自动输入。
- 人工对跟进工单的后续回答仍携带原授权/对象的来源父链。删除原授权或事实时，后续回答派生的草稿也须闭包删除，不能只终止Session而留下派生内容。

验证覆盖规则修订重评、投递但未接受、已接受窗口去重、重启、历史读取/删除、人工等待和后续人工答复的派生隐私闭包。所有收费/未知用量保留原账本，不通过测试恢复退款或清零。

## 真实模型验收的历史边界

旧master曾在缺少必填trigger_id时得到泛化SOURCE_FORBIDDEN，后来即使换新对象也把该历史错误当成全类禁止，选择ignore。当前有效调用能成功，但其语义判断未得到正例。改为明确缺参错误及通用的当前证据判断提示，仍保持鉴权失败关闭，不补猜ID或硬编码accept。

独立审核认可新冷启动observe场景：沿用同一业务数据及累计账本，保留全部旧原生/Harness历史，仅另设独立原生stateDir；新对象得到实际would_accept，零worker/工单且业务草稿不增加。该结果不代表旧master已恢复，也不替代原watch的连续链证据。累计65调用中63核实、2未知预留；脚本一次编码失败后误重复B场景属于验收控制错误，记录保留，不计为产品Red。

## 最终候选补查

独立反例确认，维护初始化把当前全部反馈当基线会掩盖初始化前新增/修改/撤回。采用先前全量priorData与最终生产完整对照、持续未处理差异及原登记全metadata保留；基线不能自动推进，检查器不授予开发权限。初始化前已存在的待capture同样不能当作已处理。

实际Linux不可变发布包启动发现缺少上游内置skills/prompts。发布manifest补入这些运行时静态资源，并增加仅manifest工件、不借源码目录的真实原生extension导入回归。Windows新CLI测试则不能假设checkout所在卷支持8.3；改在实际支持短名的TEMP隔离最小checkout验证双向别名，属于夹具可用性修正，不冒称产品修复。

隔离部署中runuser信号中继加整组SIGTERM曾使launcher清理未完成；直接用户运行的整组对照通过，但不能忽略生产同组重复投递风险。实际systemd使用KillMode=mixed：先只给官方launcher主进程SIGTERM，由它转发并等待DSH退出；超时才终止整组。验收保持端口关闭、原生持久化和私有启动文件清理要求，不删除遗留文件伪造通过。

实际异常子进程SIGKILL又确认了两层故障：启动器原先把无数值exit code误报为成功，修正为异常退出1以触发on-failure；随后新进程虽拉起，仍会撞上上游30秒owner锁，插件初始化失败而web存活。保留原生锁保护，生产RestartSec=35秒，待旧进程组清空及锁自然过期后重新启动；不强删活锁、不降低stale或添加另一套重试循环。正常优雅重启仍及时释放锁。故障恢复证据必须同时包含自动NRestarts/MainPID变化、真实Runtime ready、原数据可读及SQLite完整性，不能只看进程active。
