# P1 冻结规格 0.3.0

仅准备。共享DTO/真实宿主探针须在启动后的S1再冻结，之后才派发依赖它们的产品writer。

## 生产底座

沿用真实Runtime/Engine/Store/Effects及DSH原生Session。保留15个上游core文件；若原生接缝不足，先探针与架构决定，不能悄改core或另写Agent loop。Linux不是已有Windows通过的推论。版本锁、原生产OS/资源/Node/反代/证书和服务形态必须实际核实。

公网入口使用核实后的明确publicOrigin和受信代理配置，后端继续loopback。只信来自指定本地代理的转发信息，不信任任意Host/X-Forwarded-*；HTTP/RPC/WS、cookie、退出失效与匿名边界同时验证。HTTPS生产cookie须Secure/HttpOnly/SameSite，禁止将当前本机密码/API key直接作为公开示例。生产配置与研发GitHub/SSH凭据隔离。新增最小健康/就绪/版本探针，不能泄露数据、设置或秘密。原生getOrigin由监听地址派生，不能假称已有publicOrigin配置；项目宿主需显式向HTTP边界与native-access传递统一公网Origin。反代后登录限流不得盲信转发IP：选择保守共享限制或仅精确受信代理解析，均须反伪造验证。

发布manifest覆盖实际应用lib、vendor编译产物、锁文件、pnpm patch、profile和许可证等全部运行输入，不能仅复用当前三个lib文件的build manifest作为完整发布证明。Linux服务专用账号/UMask与control-group终止、环境HOME/TMP、软链接发布current与运行home的路径护栏关系均实际测试，不能关闭链接逃逸防护。

## 增量一：责任、阶段与人工行动

工单列表/详情投影真实Engine状态：来源、职责、授权范围、当前阶段、最新报告、Assignment摘要、等待人工原因和可执行动作；支持分页和空/错误/断线状态。工单/对话/业务任务保持不同身份，不建立第二工单权威。用户补充、回答结构化attention、重试、停止均经认证Command交给实际Engine；不得开放原生管理RPC，后端校验scope和当前版本。切换筛选不丢未提交答复，重复提交和过期答复有可解释结果。

## 增量二：明确授权的库存持续跟进

唯一首发闭环：用户对一个已存在的店铺/商品库存方案授予有限期跟进；明确业务对象、范围、期限、结束条件、允许输出（内部建议/待确认草稿）及通知条件。不存在方案/缺数据时请求补充，不能猜对象或创建无限期跟进。跟进授权持久化，工具每次检查当前范围、期限、停止和隐私epoch。

持续跟进等待变更时真实worker report waiting并保持live，目标完成才ready。机器事件不得恢复已结束工单，不越过blocked/attention/人工停止，不把普通一次性草稿任务改成永久watch。跟进到期必须通过持久生命周期关闭并拒绝后续工具；到期检查本身不调用模型。

新业务库business_events提供提交后序列引用；可信consumer持久游标，仅把白名单库存/预测/相关批次变更交给明确订阅的有效watch。事件带服务端业务引用，重新读当前事实；消息/CSV单元格/模型输出不授予权限。无关scope/对象、旧版本、缺失对象、回执、学习事件、通知、tick和助手输出不能再触发自身。可合并积压版本，但必须记录处理范围并读取最新状态，不能只标游标已消费就丢变化。

同源事件重投、消费者崩溃、换Assignment/重启只生成一次对应逻辑草稿/通知；独立新版本变化使用新稳定身份。领域计算仍确定性，模型组织解释/清单而不代替库存算法。无实质变化不通知；需要选择时真实attention→用户答复→原工单续办。任务草稿必须人工确认，禁止外部Amazon/ERP/改价/广告/消息发送。

## 增量三：唯一主动规则

首发规则：在已确认且数据有效的库存方案中，确定性计算发现缺货风险，生成内部复核候选。仅main及明确纳入的业务对象，策略版本与规则依据可追溯。默认observe，展示would-accept理由与拟执行动作，零worker启动、零业务草稿写入；原生评估可能有模型调用，必须记账，不宣称observe零模型。

auto只能在合成原生验收与独立审核通过后对这一条规则开启；单一风险窗口/业务版本去重，未变化不重复建单，已存在用户watch时优先路由其授权内工作，不建重复责任工单。禁止激活上游默认coding规则或放开全部Source事件。新权限仅限内部复核草稿，不能修改规则/凭据/代码/部署。用户关闭规则后新的候选不得接单；运行中工单收到策略变更并受执行时护栏约束。不能把修改提示词当成工具授权实现。

## 收益测量

使用同一合成库存情景分别记录普通一次性助手流程和新持续流程：人工重新提示次数、需要决策次数、遗漏事件、重复草稿/通知、端到端完成情况、耗时、模型请求和usage。P1目标：至少一次后续业务变更无需再次提示即可续办；不重复效果；仅在可用结果/必要决策/阻塞时通知。没有可比实测不宣称更快或更省；不使用自动训练/无限自学习等未实现表述。

## 研发维护隔离

每日研发维护由Codex既有独立任务接替，运营worker不持GitHub/SSH/源码能力。cc建议是受评估数据，经维护Leader分类、需求记录、规格冻结、多Agent实现及独立审核后推进；歧义和扩权保持待确认。auto运营规则与每日研发调度是两种不同授权。
